# ADR0010：已批准声明的撤销额度预留

2026-10-29。上一工作包中，普通操作可填满日志，使新的撤销也被额度拒绝。本轮在Windows开发Broker内为每份已批准声明保留一条未来撤销结果的额度。它仍是宿主声明审核，不是设备grant或活跃流撤销。

R为当前已批准声明数，O为全部保留操作数，H为宿主保留操作数。始终要求O+R不超过全局上限，H+R不超过宿主主体上限。普通应用还需满足自己的主体上限。批准先前未批准的声明消耗两格（一条结果及一格预留）；替换批准或拒绝pending消耗一格并保留旧预留。撤销已批准声明在同一事务中清空批准、释放一格预留并写入一条结果，额度占用不增加，因此普通操作无法用掉它。

预留直接从私有SQLite中批准状态派生，无内存计数或额外可漂移的计数表。所有新增修改共享同一immediate事务预算检查，幂等查询/重放先于新操作准入。重复旧操作不再次消耗或释放额度；未批准声明没有预留，新的无效力撤销仍遵循普通预算。记录全部保留，不扩大原有硬限，不静默删除承诺24小时内的记录。GetJournalCapacity仅为宿主进程内聚合诊断，不增加应用RPC。

schema提升至3以隔离不理解预留的旧写入器。schema1迁移时没有批准；schema2保留原审核版本、批准和操作，先验证所有既有结果与所需预留均在预算内，再提交版本。装不下时整个迁移失败、旧数据库保持原样，不清空批准、不淘汰记录、不自动扩大额度。需由后续受审核的离线维护/迁移方案处理这类旧状态，当前不提供自动清理入口。schema3恢复时也验证预算，降低上限不能悄悄丢弃预留。

保证仅针对逻辑日志额度：磁盘满、权限/存储损坏、锁超时、过期快照或审核版本耗尽仍可能使撤销失败，必须明确报告，不能声称无条件撤销。没有运行物理磁盘满、断电、平台实机或活跃流测试，也没有批准UI、设备授权或数据通道。仍不防止受保护数据库整体被外部旧备份回滚。
